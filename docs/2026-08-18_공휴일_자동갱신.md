# 2026-08-18 작업 기록 — 공휴일 매년 자동 갱신

마이그레이션 `202608180003_holiday_auto_sync.sql`.

0011로 공휴일 달력을 만들었지만 **관리자가 매년 직접 버튼을 눌러야** 채워졌다. 안 누르면 그 해
공휴일이 통째로 비고, 휴일근로 가산·지각 판정·휴가 일수 계산이 전부 틀어진다. 사람이 기억해야
돌아가는 장치는 언젠가 반드시 멈춘다.

회귀 테스트는 J 구간 18개를 더해 **144개**가 됐다.

## 1. 왜 크론이 아니라 '관리자가 앱을 열 때'인가

서버 혼자 돌리려면(Vercel Cron → API 라우트) **서비스 롤 키를 배포 환경에 새로 심어야 한다.**
그 키는 RLS를 전부 우회하므로, 하나 늘어나면 그만큼 샐 구멍도 늘어난다. 정작 이 일은 하루에
한 번 이상 할 필요가 없다.

관리자는 어차피 직원이라 앱을 매일 연다. 그때 조용히 채우면 새 비밀키도, 새 인프라도 필요 없다.
**얻는 것(완전 무인 갱신)에 비해 치르는 값(상시 유효한 만능 키)이 크다**고 봤다.

바꿔 말하면 이 방식의 한계는 이것이다: **관리자가 한 달 넘게 앱을 안 열면 갱신도 멈춘다.**
구성원이 늘어 관리자가 여럿이 되면 사실상 문제가 안 되고, 정말 무인으로 돌려야 할 때가 오면
그때 크론을 얹으면 된다(서버 함수는 그대로 쓸 수 있다).

## 2. 언제 무엇을 당겨오는가 — 이게 이 기능의 핵심 판단

| | |
|---|---|
| 올해 | 항상. 비어 있는 채로 굴러가는 일이 없도록 하는 안전망 |
| 내년 | **7월부터.** 한국천문연구원 특일 정보가 대개 그맘때 다음 해를 공개한다 |

내년 것을 미리 당겨오는 게 이 기능의 요점이다. "1월 1일에 아무도 안 눌러서 신정이 휴일로
안 잡힌다"가 원래 막으려던 사고인데, 12월에 이미 들어와 있으면 그 사고가 **일어날 수 없다.**
연초에 부랴부랴 받아오는 설계였다면 1월 1일 당일은 여전히 비어 있다.

### 한 번 받고 끝내지 않는다

성공한 뒤에도 **7일마다 다시 확인한다. 임시공휴일(선거일 등)은 연중에 추가되기 때문**이다.
한 번 받고 끝내면 그해 중간에 지정된 휴일을 영영 모른다.

다시 받아도 안전한 이유는 `overwrite=false`다(0011). 이미 등록된 날짜는 손대지 않으므로
관리자가 고친 이름과 자체 휴일(창립기념일 등)이 덮이지 않는다. G-4 케이스가 이걸 지킨다.

### 실패는 더 짧게, 성공은 더 길게

| 마지막 상태 | 다시 시도 |
|---|---|
| 한 번도 성공 못 함 | 1일 뒤 |
| 성공한 적 있음 | 7일 뒤 |

키가 빠졌거나 API가 죽었을 때 앱을 열 때마다 두드리면 안 된다. 그렇다고 7일을 기다리면
문제를 고쳐 놓고도 일주일을 기다려야 한다. 그래서 실패는 하루로 잡았다.

## 3. 상태를 기기가 아니라 DB에 둔 이유

`localStorage`에 "마지막 갱신일"을 두면 기기마다 따로 놀고, 시크릿창에서는 매번 다시 돈다.
이 저장소에는 이미 같은 실수의 기록이 있다 — 퀘스트 보상이 localStorage에만 있어서 시크릿창에서
중복 수령이 됐던 버그(8/8). 그래서 `work_holiday_syncs`(워크스페이스 × 연도) 한 행으로 두고,
**언제 다시 당길지는 서버가 판단**한다(`holiday_sync_due`).

### 가져오기 전에 자리를 맡아 둔다

`record_holiday_sync`를 가져오기 **전에** 한 번(실패 상태로), 끝나고 한 번 부른다.
미리 맡아 두지 않으면 가져오는 중에 브라우저를 닫았을 때 시도 시각이 안 남아, 다음 접속 때
곧바로 또 두드린다. **실패에도 제동이 걸려야 한다.**

### 실패해도 지난 성공은 지우지 않는다

관리자에게 필요한 정보는 "마지막으로 성공한 게 언제인가"다. 실패 기록이 그걸 덮으면
갱신이 언제부터 멈춰 있었는지 알 수 없다. `succeeded_at`은 성공했을 때만 갱신한다(J-8).

## 4. 일반 구성원에게는 예외가 아니라 빈 배열

`holiday_sync_due`는 **로그인한 모든 사용자가 앱 시작 때 부른다**(`AppShell` → `HolidayAutoSync`).
관리자가 아니면 권한 오류를 던지는 대신 `[]`를 돌려준다. 일반 구성원이 앱을 열 때마다
콘솔에 오류가 찍히면 진짜 문제를 못 알아본다.

쓰기(`record_holiday_sync`)는 반대로 관리자만 허용한다. 읽기 판단과 쓰기 권한을 다르게 둔 자리다(J-2, J-3).

## 알려진 한계

- **관리자가 앱을 오래 안 열면 갱신도 멈춘다** (위 1번). 지금 구성원 수에서는 감수할 만하다.
- 관리자 두 명이 동시에 앱을 열면 같은 해를 두 번 받아올 수 있다. 저장이 `overwrite=false`라
  결과는 같고 API를 한 번 더 부르는 정도라 막지 않았다.
- 워크스페이스는 `attendanceWorkspaceId()`가 주는 첫 번째 것만 본다(앱 전체가 쓰는 방식과 동일).
  한 사람이 여러 워크스페이스의 관리자면 나머지는 수동으로 눌러야 한다.
- 자동 갱신은 `public_api` 출처만 쓴다. CSV 업로드는 지금처럼 수동이다.
