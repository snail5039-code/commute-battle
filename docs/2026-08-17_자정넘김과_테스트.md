# 2026-08-17 작업 기록 — 자정 넘김 버그와 회귀 테스트 도입

마이그레이션 `202608170010_overnight_work_date.sql`, 테스트 `supabase/tests/attendance.sql`.

---

## 1. 무엇이 문제였나

야근해서 자정을 넘겨 퇴근하면 출근은 어제 `date`, 퇴근은 오늘 `date`로 저장됐다.
`get_attendance_summary`가 `date`로 묶으니 어제 행에는 `work_out`이 없고 오늘 행에는 `work_in`이
없다. 양쪽 다 **'기록 미완료' → 근무시간 0분**. 가장 오래 일한 날이 집계에서 통째로 사라진다.

기능 부재가 아니라 임금이 0이 되는 버그다. 그래서 로드맵 순서를 바꿔 먼저 잡았다.

**실제 데이터 확인**: 불균형한 날 9건은 전부 `출근 > 퇴근`(도착을 안 찍고 버린 테스트 잔재)이고,
`퇴근만 있는 날`은 0건이었다. 즉 아직 실제로 자정을 넘긴 기록은 없었다 — 백필 대상 없음.

## 2. 어떻게 고쳤나 — 근무일(work date) 귀속

기록에 근무일 개념을 넣었다.

- 출근(`commute`) = 항상 오늘
- 퇴근(`return`) = **아직 퇴근으로 닫히지 않은 가장 최근 근무일**(어제까지). 없으면 오늘

`attendance_work_date(user, stamped)`가 판정한다. 규칙은 "어제~오늘 중 `출근 수 > 퇴근 수`인
가장 최근 날짜". 어제·오늘이 둘 다 열려 있으면 오늘이 이긴다. 사흘 전 잔재는 보지 않는다 —
그건 정정 요청으로 바로잡을 대상이지 오늘 퇴근을 끌어갈 근거가 아니다.

**집계 계산식은 한 줄도 손대지 않았다.** 확인해 보니 이미 자정 넘김을 견디게 짜여 있었다.

| 계산 | 자정 넘김에서 |
|---|---|
| 야간 | 두 번째 항이 `(date 22:00 ~ date+1 06:00)`이라 익일 새벽까지 덮는다 |
| 조기퇴근 | `scheduled_out - work_out`이 음수 → `greatest(0, …)`로 0 |
| 휴일 | 출근한 날 기준. 토요일 출근 → 일요일 새벽 퇴근이 토요일 휴일근로로 잡힌다 |

날짜만 제대로 물려주면 나머지가 따라온다는 뜻이다.

## 3. 함께 잡은 회귀 두 개

**(1) 중복 퇴근이 가능해질 뻔했다.** 중복 차단이 `date = 오늘`이었는데, 퇴근 기록의 `date`가
어제가 되면 그 기록을 못 본다. 새벽 1시에 퇴근을 누르고 1시 5분에 또 누를 수 있게 된다.
차단 범위를 '어제~오늘'로 넓혔다. 0005가 피하려던 것(며칠 전 잔재가 새 출근을 영구히 막는 것)은
그대로다 — 사흘 전 미완결은 여전히 막지 않는다.

**(2) 화면에서 퇴근 버튼이 아예 안 눌렸다.** 이게 사실 더 심각했다. `CommuteButton`이 `today`
기준으로만 세니 새벽 1시엔 `commuteCount=0, returnCount=0`이 되고, 퇴근 버튼의 비활성 조건
`commuteCount <= returnCount`에 걸려 **퇴근을 기록할 방법 자체가 없었다.** 도착 처리 버튼도
어제 기록을 못 찾아 안 나왔다. 클라이언트도 서버와 같은 규칙으로 근무일을 계산하게 고쳤다.

브라우저로 두 시나리오를 확인했다(임시 페이지, 확인 후 되돌림):

- 어제 출근 완료 + 퇴근 미기록 → 퇴근 버튼 **활성**, "설정한 퇴근 시간이 지났어요" 안내
- 어제 이동 중 기록 → "무사 도착!" 버튼 노출, "출근 중입니다"

## 4. 회귀 테스트 도입 (`supabase/tests/attendance.sql`)

지금까지 매 세션 롤백 DO 블록으로 검증하고 **버렸다**. 임금에 영향을 주는 계산이 계속 늘어나는데
회귀를 잡을 장치가 없었다. 버리던 걸 파일로 남겼다.

- 54개 검사, 한 트랜잭션, 마지막에 예외를 던져 전부 롤백. 결과는 예외 메시지로 나온다.
- **합성 계정·워크스페이스를 트랜잭션 안에서 만들어 쓴다** — 실제 데이터에 의존하지도, 건드리지도
  않는다. 워크스페이스가 `auth.users`를 참조해서 `auth.users`에도 합성 행을 넣는다(id 외에는 전부 기본값).
- 범위: 근무시간 6종 계산(A) · 자정 넘김(B) · 근무일 귀속 규칙(C) · 기록 RPC와 중복 차단(D) ·
  위치 판정(E) · 함수 권한(F)

왜 SQL 테스트인가: 계산이 전부 Postgres 함수 안에 있다. JS 테스트로는 한 줄도 못 덮는다.
`npm test`로 자동화하지는 않았다 — 러너를 붙이려면 Postgres 접속 문자열이 필요한데 저장소에
두고 싶지 않은 값이다. 지금은 수동 실행이고, 실행법은 `SETUP.md`에 적었다.

### 테스트를 쓰다가 테스트가 먼저 틀렸다

처음 돌렸을 때 13건이 실패했다. 원인은 픽스처의 괄호였다.

```sql
d1 + time '08:00' at time zone 'Asia/Seoul'    -- d1 + (time at time zone …) 로 파싱 → 9시간 밀림
(d1 + time '08:00') at time zone 'Asia/Seoul'  -- 이게 맞다
```

`AT TIME ZONE`이 `+`보다 강하게 결합한다. 집계 함수 쪽은 원래 괄호가 있어서 멀쩡했고, 새로 쓴
픽스처만 틀렸다. 하네스가 실제 값을 `기대=… 실제=…`로 뱉어 줘서 바로 잡혔다 —
테스트가 자기 값어치를 첫 실행에서 증명한 셈이다.
