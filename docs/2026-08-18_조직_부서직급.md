# 2026-08-18 작업 기록 — 조직 (부서·직급)

마이그레이션 `202608180004_org.sql`. 회귀 테스트 K 구간 25개를 더해 **169개**가 됐다.

지금까지 워크스페이스 안의 사람은 전부 평평했다. 근무시간 집계는 전원을 한 줄로 늘어놓을 뿐이라
"개발팀만 보자"가 안 되고, 명단에도 누가 무슨 일을 하는지 안 나왔다.

---

## 1. 시작하자마자 부딪힌 것 — `departments`가 이미 있었다

마이그레이션을 적용하니 `column "workspace_id" does not exist`로 죽었다.
**`public.departments` 테이블이 이미 있었다.** 0100001의 부서 채팅 채널 테이블이다
(전체 공지·개발팀·디자인팀·마케팅팀·운영팀 5행, `department_messages`가 참조).

`create table if not exists`가 조용히 넘어가고, 그 다음 `create index ... (workspace_id, ...)`가
없는 컬럼을 짚어서 터진 것이다. **`if not exists`는 "같은 것이 있다"를 보장하지 않는다 —
이름만 같아도 넘어간다.**

SETUP.md에 적혀 있던 "파일이 항상 진실은 아니다"에 그대로 걸렸다. 다음부터는 테이블을 만들기 전에
`to_regclass`로 이름부터 확인할 것.

확인해 보니 그 테이블과 `department_messages`는 **앱 코드 어디에서도 참조하지 않는다**
(채팅은 `chat_channels`/`chat_messages`로 옮겨갔다). 죽은 테이블로 보이지만 지우는 건 이 작업의
범위가 아니라서 건드리지 않고 `org_departments`/`org_positions`로 비켜 갔다.

부분 적용이 남지 않았는지 확인했다: `chat_workspace_members`에 컬럼이 안 붙었고
`org_positions`도 안 만들어졌다. 기존 `departments`의 RLS·권한도 그대로다.

## 2. 정한 것

### 부서는 평면이다

상위 부서(본부 > 팀)를 두지 않았다. 계층을 넣으면 순환 방지와 재귀 집계가 따라오는데,
지금 그걸로 모델링할 실제 조직이 없다. 필요해지면 `parent_id`를 추가하고 집계를 재귀로
바꾸면 된다. 지금 넣으면 쓰지도 않는 복잡도만 남는다.

### 직급은 권한이 아니다 — 이게 가장 중요한 선

`rank`는 화면에 늘어놓는 순서일 뿐이다. 무엇을 보고 무엇을 승인할 수 있는지는 지금처럼
role(owner/admin/member)이 정한다.

이 둘을 섞으면 "부장이니까 남의 근태를 본다" 같은 규칙이 슬금슬금 생기고, 그때부터는
권한이 어디서 오는지 아무도 설명하지 못하게 된다. 관리자 화면에도 이 문장을 적어 뒀다 —
안 적어 두면 "부장으로 올려주면 남의 근태를 볼 수 있나?"라는 오해가 반드시 생긴다.

### 근무시간 집계 함수는 건드리지 않았다

`get_attendance_summary`는 임금이 걸린 계산이라 손댈 때마다 위험하다. 부서를 표시하려고
그 함수를 고치는 대신, 화면이 `list_org`로 부서를 따로 받아 `userId`로 맞춰 붙인다.
결과는 같고 위험은 없다. 부서 필터도 이미 받아 온 행을 거르는 것으로 처리한다.

### 부서를 지워도 사람과 기록은 남는다

`on delete set null`이라 배정만 풀린다. 조직 개편이 근태 기록을 지우는 일이 되면 안 된다.
직급은 따로 남는다(부서를 지웠다고 직급까지 날아가지 않는다 — K-11).

### 겸직은 없다

사람과 조직은 1:1이다. 겸직을 넣으려면 "근무시간을 부서별로 어떻게 나눠 다는가"라는
훨씬 큰 문제를 먼저 풀어야 한다.

## 3. 보는 것과 바꾸는 것을 다르게 뒀다

| | 조직도 보기 | 부서·직급 만들기 / 배정 |
|---|---|---|
| 일반 구성원 | **가능** | 불가 |
| 관리자 | 가능 | 가능 |

누가 어느 팀인지는 사내에 공개된 정보다. 근태와는 다르다 — 근태는 관리자만 남의 것을 본다.
K-12(보기 허용)와 K-13(바꾸기 금지)이 이 선을 지킨다.

## 4. 외래키로는 못 막는 것

`assign_member_org`는 부서가 **그 워크스페이스의 것인지** 직접 확인한다. 둘 다
`org_departments`이므로 외래키 참조 자체는 유효해서, 남의 워크스페이스 부서 id를 넣으면
그냥 붙어 버린다. K-8이 이걸 지킨다.

## 5. 화면

- `/admin`에 **조직 (부서·직급)** 카드를 근무시간 집계 바로 위에 뒀다. 부서를 먼저 정해야
  집계를 부서별로 볼 수 있으므로 순서가 그렇게 된다.
- 부서·직급은 이름을 눌러 바로 고친다(포커스가 빠질 때 저장). 낙관적 갱신은 하지 않는다 —
  서버가 거절하면 화면과 DB가 갈라진다.
- 근무시간 집계에 **부서 필터**와 **부서 열**이 붙었다. 합계·주52시간 경고·CSV까지 전부
  걸러진 결과를 본다(`view`). 합계만 전체 값으로 남으면 필터가 거짓말이 된다.
- 부서가 하나도 없으면 필터와 열이 아예 안 보인다. 안 쓰는 조직에 빈 칸을 보여 줄 이유가 없다.

## 6. 이름 바꾸기에서 자기 자신 예외

`save_department`의 중복 검사는 `target_id is null or d.id <> target_id`다. 이 예외를 빼먹으면
순서만 바꾸려 해도 "이미 있는 이름"이라고 막힌다. K-6이 이걸 지킨다.

## 알려진 한계

- **관리자 화면을 브라우저로 눌러 보지 못했다.** 로그인 뒤에 있고 계정 정보가 없다.
  타입·린트·빌드는 통과했고 DB는 K 구간 25개로 검증했지만, 실제 화면 동작은 사용자가
  확인해야 한다. (dev 서버로 랜딩 페이지 렌더와 `/admin` 로그인 리다이렉트까지는 확인했다 —
  서버·콘솔 오류 없음)
- 승인 라인(부서장이 자기 부서 근태 정정을 승인)은 아직 없다. 그러려면 부서장을 정하는
  개념이 필요한데, 그건 위에서 정한 "직급은 권한이 아니다"와 어떻게 어울릴지 먼저 정해야 한다.
- 부서별 합계(부서 단위 근무시간 총계)는 없다. 지금은 부서로 거르고 전체 합계를 보는 방식이다.
- 죽은 `departments`/`department_messages` 테이블은 그대로 뒀다(위 1번).
